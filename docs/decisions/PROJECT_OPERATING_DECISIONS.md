# TRACÉ RAFFINÉ — قرارات المشروع ونظام التنفيذ

آخر تحديث: 2026-10-11

## 1. بنية التطبيقات — قرار ثابت

- `D:\TR`: تطبيق المصممين والعملاء، تطبيق Flutter مستقل يستهدف Android وiOS.
- `D:\TR_ADMIN`: تطبيق الإدارة، مشروع Flutter مستقل ووجهته الويب.
- يمنع خلط مسارات المصدر أو أوامر البناء أو النشر بين التطبيقين. قبل أي نشر، افحص المسار الفعلي في `appwrite.config.json`، ومعرّف المورد، ومصدر البناء.
- الاتصال الحالي الذي تم التحقق منه: Appwrite project `trace-raffine`، endpoint الخاص بالمشروع `https://fra.cloud.appwrite.io/v1`، قاعدة البيانات `tr_database`. لا تنشئ مشروعًا ثانيًا ولا تغيّر الاتصال إلا بدليل وخطة انتقال واضحة.
- وجود موقع الإدارة `tr-admin` لا يعني أن تطبيق الهاتف يجب أن يكون موقع ويب؛ تطبيق المصمم يُبنى كحزمة Android/iOS.

## 2. الهوية البصرية

- الاتجاه المعتمد: Editorial / High-Fashion أوروبي فاخر، هادئ ومقصود، مناسب لمنتج أزياء وملفات digitizing.
- تجنّب Material Design التقليدي والقوالب العامة والاعتماد المفرط على البطاقات المتكررة.
- لا تنفذ تغييرات بصرية كبيرة قبل مراجعة الشاشات والمكونات الفعلية والحفاظ على السلوك الوظيفي.

## 3. قانون العمل الهندسي

1. اجمع الأدلة الفعلية من المصدر المناسب قبل التغيير: ملفات، استدعاءات، إعدادات، سجلات، مخطط البيانات، تغييرات Git، ونتائج التشغيل.
2. حدّد السبب الجذري أو الفجوة المثبتة، وافصل الحقيقة عن الفرضية.
3. نفّذ أصغر تغيير يحقق المطلوب ويحافظ على العقود والبيانات والصلاحيات القائمة.
4. شغّل الاختبار الذي يثبت السلوك المتأثر، ثم الاختبارات الرجعية والتحليل والبناء الملائمين.
5. سجّل ما عُدّل، وما نجح اختباره تحديدًا، وما بقي غير متحقق منه، وأول خطوة تالية.

ممنوع: تخمين المسارات أو الصلاحيات، تحديث الحزم عشوائيًا، حذف ملفات/بيانات قبل إثبات عدم استخدامها، أو إعلان نجاح رحلة كاملة اعتمادًا على build/analyze فقط.

## 4. خطة العمل الأساسية ذات الخمس خطوات

1. **فحص الحالة الحالية:** مقارنة المصدر المحلي بالإعدادات والخادم، والحفاظ على التغييرات الحالية.
2. **قوائم المصممين:** تصنيف كل عنصر إلى إبقاء/تعديل/حذف، وفحص الاعتماديات قبل التنفيذ.
3. **قوائم العملاء:** مراجعتها بشكل مستقل عن قوائم المصممين والإدارة.
4. **التكامل من البداية إلى النهاية:** تتبع البيانات بين `D:\TR` و`D:\TR_ADMIN` وAppwrite، بما يشمل الهوية والأدوار والرسائل والإشعارات والتصاميم والملفات.
5. **اختبارات واقعية:** اختبارات الوحدة والتكامل والواجهة ورحلات المستخدم، مع فصل نتائج المحاكاة عن نتائج الحسابات الفعلية وعن اختبار الهاتف الحقيقي.

## 5. قاعدة التوثيق والاستئناف

- Notion هو مرجع قرارات المشروع، الحالة، الأدلة المؤكدة، والعوائق ونقطة الاستئناف.
- هذه الملفات تحت `docs/` تحفظ نسخة قريبة من الكود من القرارات التشغيلية والمكونات الإضافية.
- Linear هو سجل المهام والأخطاء والأولويات ومعايير القبول؛ لا تغلق مهمة لمجرد تغيير الكود.
- GitHub هو مصدر التاريخ التقني والتغييرات المراجعة. لا تنفذ commit/push شاملًا مع وجود تغييرات محلية غير مرتبطة أو غير مراجعة.
- نهاية كل جلسة عمل ذات معنى: تحديث Notion وملف الحالة، تسجيل الاختبارات ونتائجها، وتحديد الخطوات الثلاث التالية.
- الهدف اليومي المرجعي 8 ساعات عند العمل اليومي، مع فترات راحة وجلسات طويلة؛ الجودة والتحقق مقدمان على العدد أو الجدول.

## 7. بوابة النشر

قبل أي نشر: (أ) تحديد التطبيق والمجلد، (ب) تحديد المورد/المعرف النشط في Appwrite، (ج) مراجعة diff، (د) الاختبارات الملائمة، (هـ) النشر، (و) التحقق من حالة deployment، (ز) اختبار فعلي بعد النشر. إذا تعذّر آخر بند، وثّق العائق ولا تدّع اكتمال الرحلة.
