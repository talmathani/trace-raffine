# TRACÉ RAFFINÉ — المكونات والأدوات الإضافية

آخر تدقيق: 2026-10-11. هذا سجل لقدرات تم فحصها، وليس افتراضًا بأن كل تكامل مكتمل.

## توزيع الأدوار

| المكوّن | المسؤولية | قاعدة الاستخدام وحد الإثبات |
|---|---|---|
| Remote Desktop Commander | ملفات Windows، PowerShell، السجلات، البناء والاختبارات | استخدمه لفحص الحالة الفعلية. بدء العملية ليس نجاحًا؛ اقرأ المخرجات ورمز الخروج. |
| Appwrite | المصادقة، قاعدة البيانات، التخزين، الوظائف، الفرق والصلاحيات والمواقع بحسب الكود | افحص IDs والصلاحيات والتدفق الفعلي؛ حالة الخدمة لا تثبت رحلة المستخدم. |
| GitHub | المستودع، الفروع، تاريخ الكود، diff وActions | قارن المصدر المحلي بالفرع؛ لا ترفع تغييرات محلية غير مراجعة كدفعة واحدة. |
| Linear | المهام، الأخطاء، الأولويات، معايير القبول والحالة | لا تغلق مهمة قبل اختبار معيار القبول. |
| Notion | القرارات، النتائج، العوائق ونقطة الاستئناف | حدّثه بعد كل مرحلة عمل ذات معنى. |
| Figma | الشاشات، المكونات، المتغيرات والهوية البصرية | يلزم ملف محدد وصلاحية مناسبة؛ التصميم لا يثبت صحة الكود. |
| Ansight | فحص التطبيق الحي، الشجرة المرئية والتفاعل والسجلات | لا تدّع جلسة حية دون Session ID واتصال ناجح. |
| Amplitude | أحداث المنتج، التحويل، التفاعل والاحتفاظ | لا تستنتج شيئًا قبل تأكيد المشروع ومخطط الأحداث وجودة البيانات. |
| Superpowers | منهجية التخطيط وتصحيح الأخطاء وTDD والتحقق | المهارات توجه العملية ولا تستبدل تشغيل الاختبارات وقراءة النتائج. |
| الاختبارات | إثبات سلوك محدد واكتشاف التراجعات | وثّق نطاق الاختبار وحدوده؛ نجاح unit test ليس E2E. |

## حالة الاتصالات المؤكدة

### Appwrite
- المشروع `trace-raffine` في منطقة `fra` بحالة `active`؛ قاعدة `tr_database` بحالة `ready`.
- Storage الظاهر: `design-files`.
- Functions المفعلة: `create-order` و`admin-user-control`. أحدث نشر `create-order`: `6acbf4193832a1e0dc07`؛ أحدث نشر `admin-user-control`: `6acbebdca5db88f7fbf3`.
- موقع الإدارة `tr-admin` موجود ومفعل بإعداد Flutter Web. لا تستخدمه لنشر تطبيق المصمم.
- Messaging service ظهر بإجمالي 0 في ملخص الموارد. هذا لا يثبت غياب إشعارات التطبيق؛ فقد يستخدم التطبيق قاعدة البيانات والوظائف. تتبع الكود الفعلي قبل الحكم.

### GitHub وLinear وNotion
- GitHub: `talmathani/trace-raffine`، الفرع الافتراضي `main`. الشجرة المحلية تحتوي تغييرات كثيرة غير ملتزمة؛ راجع `git status` وdiff قبل أي commit/push.
- Linear: الفريق `TRA` ومشروع `TRACÉ RAFFINÉ` موجودان. المهمة التشغيلية الموجودة `TRA-5` — تنفيذ التحقق التشغيلي والبناء.
- Notion: مرجع المشروع «TRACÉ RAFFINÉ — مرجع المشروع واتفاق العمل»، وبروتوكول «TRACÉ RAFFINÉ — بروتوكول التنفيذ والتحقق الإجباري».

### Figma — وصول جزئي
- نجح `whoami`، لكن المقعد المعروض View على خطة Starter، ولم يُحدد ملف تصميم في هذا التدقيق.
- لا ندّعي تحرير ملف ولا نغيّر التصميم قبل التأكد من الملف والصلاحية. عند استخدام أدوات Figma التي تتطلب ذلك، اقرأ المهارة التمهيدية الإلزامية أولًا.

### Amplitude — المشروع يحتاج تأكيدًا
- سياق الحساب يعرض مشروعًا واحدًا باسم `default` ومعرّف `868898`.
- بحث عن أحداث عرض التصميم/تفاصيل المنتج/السلة/الدفع/الشراء/التنزيل أعاد صفر نتائج. لم يثبت بعد أن `default` هو مشروع TRACÉ RAFFINÉ؛ لا تُنشأ لوحات أو استنتاجات تجارية قبل التأكد من المشروع ومخطط الأحداث.
- لا تُرسل كلمات مرور أو بيانات دفع أو بيانات شخصية غير لازمة. الارتباط لا يثبت السببية.

### Ansight — CLI جاهز جزئيًا، ولا جلسة تطبيق
- الإصدار `1.0.1`. فحص `ansight doctor --json` أعاد `isHealthy: true` مع تحذيرات أدوات اختيارية غير مثبتة: `dotnet-trace` و`dotnet-dsrouter` وTesseract وscrcpy.
- المضيف متوقف وحالته قديمة، وقائمة التطبيقات فارغة والجلسات المتصلة صفر.
- ADB متاح لكن Android Emulator executable غير موجود. لا تثبت أدوات اختيارية ولا تعدّل التطبيق لمجرد غياب الجلسة؛ تحقق من التكامل الحالي أولًا.

### Superpowers — منهجيات تُستخدم دوريًا
- `brainstorming` قبل إضافة سلوك أو ميزة جديدة.
- `systematic-debugging` عند الأعطال قبل اقتراح الإصلاح.
- `writing-plans` للعمل متعدد الخطوات، و`test-driven-development` عند إصلاح/إضافة السلوك.
- `verification-before-completion` قبل إعلان الاكتمال أو نجاح الاختبار.
- اتبع مهارات Figma وAnsight التمهيدية الإلزامية قبل الأدوات التي تشترطها.

## دورة العمل المتكررة
1. استرجاع آخر نقطة من Notion وLinear ومقارنتها بالحالة الفعلية.
2. اختيار الأدوات الملائمة وجمع الأدلة المرتبطة في مرور واحد قدر الإمكان.
3. تحديد السبب الجذري أو الفجوة المثبتة.
4. أصغر تغيير مبرر مع الحفاظ على البيانات والصلاحيات والتغييرات الحالية.
5. تشغيل الاختبارات الملائمة وقراءة المخرجات ورمز الخروج.
6. مراجعة diff والمسار الصحيح.
7. تحديث Notion وLinear وملفات docs؛ تحديث GitHub فقط بعد مراجعة التغيير المناسب.

## دورية الاستخدام
- بعد كل إصلاح/ميزة: حدث Linear بنتيجة الاختبار.
- بعد كل مرحلة/جلسة ذات معنى: حدث Notion و`PROJECT_STATUS.md`.
- قبل النشر: افحص Appwrite IDs والمسار المحلي والاختبارات.
- عند تغيير واجهة: استخدم Figma إذا توفر ملف وصلاحية، ثم اختبر الواجهة.
- استخدم Amplitude بعد تأكيد المشروع والأحداث، وAnsight عند توفر جلسة حية.
